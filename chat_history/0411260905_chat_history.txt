sender james@myadventuregroup.com.au) -> Supabase "Create a row"

Diagnosed root cause: the v1 Supabase node with auto-map sends ALL items as a
single PostgREST BULK insert, which requires every object to have an identical
key set. The Gmail items differ (some have Cc, some don't), so the batch is
rejected. Not a table/column problem.

Fix: inserted a Code node ("Normalize keys") between Gmail and Supabase that
maps every item to the same fixed 12 keys, filling missing ones (e.g. Cc) with
null and dropping any stray keys without a column. Wrote the corrected workflow
to "Gmail Email Samples Caching (fixed).json" (Schedule -> Get many messages ->
Normalize keys -> Create a row). Gave both import and manual-add instructions
plus the Code snippet.

pulls the latest 20 each run, so overlapping ids will cause a duplicate-key
(23505) failure on the next run because the v1 node does a plain insert (no
upsert). Recommended either an HTTP Request node with
`Prefer: resolution=merge-duplicates` (PostgREST upsert) or a dedup step, and
offered to wire up the upsert version. (Left pending the user's choice.)
